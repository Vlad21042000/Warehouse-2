# Cloud accounts setup

Dedicated project: `wjmchfuufqkjjimwwxbs` (Warehouse Reporting, ca-central-1). The schema was applied as `warehouse_accounts_and_reports`; the security advisor returned no findings. Production site and redirect URLs are configured. Minimum Auth password length is set to 12 and email confirmation remains enabled. Brevo SMTP is enabled with the verified owner sender; full email delivery and production Auth flows still need verification. Production Vercel variables are configured; end-to-end Auth verification remains required. Do not apply this schema to another application's database.

1. Confirm the organization and project cost with the owner, then create the Warehouse Reporting project.
2. Apply `schema.sql` as a recorded Supabase migration. Run Supabase security advisors after application.
3. Configure Auth's site URL as `https://warehouse-2-sigma.vercel.app` and allow the exact production root as an email redirect. Keep email confirmation enabled and enforce at least 12 password characters in Auth settings.
4. Configure a production SMTP provider in Supabase's secure settings. Supabase's default email service is restricted and is unsuitable for public registration. Verify confirmation and password recovery delivery before opening registration.
5. Set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` in Vercel and local development. Never put a secret key, service-role key or SMTP password in Vite variables, GitHub or chat.
6. Have the owner register and verify the agreed email. Using a trusted administrator operation, merge `warehouse_role: 'owner'` into that exact Auth user's `app_metadata`. Preserve other metadata and verify the user's ID, email and email confirmation. Never authorize by client-controlled `user_metadata` or an email hardcoded in the frontend. Have the owner sign in again to refresh the JWT.
7. Test two ordinary accounts and the owner in production: registration, verification, recovery, save/open, cross-device history, two-report comparison, archive/restore, account isolation and owner access. Verify logout clears opened account data and that printing still produces one page.

Reports retain the selected day's transaction lines, including optional order/item fields, for later charts and comparison. Each snapshot is limited to 10 MB and 200,000 transactions. Exact duplicate snapshots are rejected per user and date. Counts are generated by Postgres from the saved payload.

The registration notice explains that the site owner can view saved reports. The owner dashboard lists registration email, registration date, verification status, last sign-in and saved reports; passwords and tokens are never exposed. Owners can read other users' reports but cannot modify them through this frontend. Users archive and restore their own reports; there is no permanent-delete action.

`npm test` exercises snapshot validation and executes the schema in an isolated PGlite Postgres instance with real roles and RLS policies. It covers forged user metadata, cross-account inserts/reads/updates, owner read access, restricted profile writes, invalid payloads and anonymous denial. These checks complement the production Auth and browser verification required above.
